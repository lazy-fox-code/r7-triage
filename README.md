# r7-triage

Расширение для Р7-Органайзера (Thunderbird 115.12.2), которое строит граф
деловой переписки и отделяет поручения от информирования. Классификация
выполняется локально развёрнутой моделью. Данные не покидают периметр.

---

## Зачем

Корпоративный ящик на десятки тысяч писем содержит три принципиально разных
потока, которые почтовый клиент не различает:

- **поручения** — от меня ждут действия, у него есть срок и автор;
- **информирование** — мне сообщили, действие не требуется, ценность падает
  со временем;
- **шум** — автоматика, рассылки, уведомления систем.

Ручная сортировка этих потоков занимает часы в неделю и делается плохо.
Задача расширения — делать её автоматически, с понятной пользователю
мотивировкой каждого решения.

## Что должно получиться

Четыре функции, в порядке приоритета реализации:

### 1. Граф переписки

Направленный граф «кто кому пишет». Узлы — люди, рёбра — потоки писем
с метриками:

| Метрика | Зачем |
|---|---|
| число писем, суммарный и медианный объём | базовая интенсивность |
| доля ответов с моей стороны | насколько отправитель для меня значим |
| медианная задержка моего ответа | прокси иерархии, см. п.2 |
| отношение To:CC | сильнейший дешёвый признак поручения |
| доля инициированных веток | кто задаёт повестку |
| глубина и ветвление тредов | обсуждение против вещания |

**Важно про постановку.** Метрики графа сами по себе поручение от
информирования не отделяют: рассылка от руководителя и поручение от него
же дают одинаковое ребро. Разделяет текст письма. Граф нужен для другого —
он даёт дешёвые признаки, позволяющие **не звать модель** на большинстве
писем, и калибрует пороги под конкретного отправителя.

### 2. Поручения с учётом уровня отправителя

Уровень отправителя влияет на приоритет и срок поручения, но **не** на сам
факт классификации. Просьба от коллеги-ровесника обязана оставаться
поручением.

Источники уровня, по убыванию надёжности:

1. **LDAP / AD / GAL** — должность и поле manager. Факт, а не догадка.
   Основной источник, если каталог доступен.
2. **Вывод из графа** — для внешних контактов и как запасной путь.
   Рабочая эвристика: асимметрия задержки ответа (начальнику отвечают
   быстро, подчинённому — когда дойдут руки), направление инициации веток,
   веерность рассылок. Это эвристика, жёсткие правила на ней строить
   нельзя.

### 3. Делегирование по исполнителям

Для извлечённого поручения предложить исполнителя. Модель компетенций
строится из того же графа: кто раньше участвовал в ветках близкой
тематики и доводил их до ответа. Тематика — кластеризация по эмбеддингам,
не через LLM.

Результат — предзаполненный черновик через `compose.beginNew`.
**Автоотправка не реализуется ни в каком виде.** Письмо, ушедшее без
просмотра человеком, стоит дороже всей экономии времени.

Кто ваши сотрудники, расширение понимает из переписки: если к вам обратились,
вы промолчали, а ответил коллега — он закрывает вопросы за вас. Письмо, на
которое ответил такой сотрудник, для вас информирование, а не поручение.

### 4. Устаревшее информирование

Три ступени вместо удаления:

1. тег `Информирование` + расчётная дата истечения, ничего не двигается;
2. через N дней — автоперенос в папку «Архив информирования», обратимо;
3. удаление — **только** пакетом, по явной команде, со списком на просмотр.

Жёсткие исключения из-под правила: есть вложения, есть мой ответ в ветке,
стоит флаг, отправитель выше по уровню.

Перед включением любой ступени проверить регламент хранения корпоративной
почты: во многих организациях автоудаление запрещено.

## Архитектура

Расширение — единственный артефакт установки. Внешних процессов на машине
пользователя нет: это было явным стоп-фактором.

```
Р7-Органайзер (Thunderbird 115)
└── r7-triage (MV2, персистентный background)
    ├── background.js     два прохода: свежее сразу, архивы в простое
    ├── scan.js           окна по дате, чекпойнты, дедупликация
    ├── enrich.js         полные заголовки: ветки, рассылки, встречи
    ├── features.js       дешёвые признаки и гейт
    ├── keys.js           устойчивые ключи писем и папок
    ├── worker: graph     инкрементальные метрики рёбер
    ├── worker: llm       пул запросов, конкурентность 2–4
    ├── IndexedDB         messages, edges, people, verdicts, tasks, meta
    └── ui/panel          граф, список поручений, разбор решений
                │
                ↓ fetch, /v1/chat/completions
        DeepSeek (локально или на общем инференс-хосте)
```

Почему без сайдкара на Python: IndexedDB держит нужные объёмы, воркеры
дают параллельность, а второй устанавливаемый компонент означал бы второй
объект согласования со службой безопасности.

### Откуда берутся письма

Расширению не нужно реализовывать сетевые протоколы. Почта в
Р7-Органайзере доступна как обычные папки Thunderbird, и работают штатные
`browser.messages.query` / `getFull` / `getRaw` / `update`.

Оговорка: часть писем может отсутствовать в офлайн-хранилище, и первый
полный проход потянет их с сервера. Перед массовым разбором включить
хранение сообщений офлайн.

## Конвейер разбора

Порядок принципиален. На ящике в 50 000 писем при секунде на вызов модель
будет работать 14 часов, поэтому до модели доходит меньшинство.

Порядок — LIFO. Свежая почта разбирается при запуске клиента и по приходу,
архивы догоняются в простое: ждать часы ради первой пометки нельзя.

```
1. Перечисление        browser.messages.query окнами по дате, постранично.
                       Только то, что отдаёт MessageHeader: тело не читаем
2. Дешёвые признаки    заголовки, без тела:
                       · List-Unsubscribe, Precedence: bulk,
                         Auto-Submitted  → шум, модель не зовём
                       · профиль отправителя: система, вещание, человек
                       · To против CC, поимённая адресация
                       · известность отправителя по графу
3. Гейт                кандидат в поручения? иначе дефолтный вердикт
4. Модель              только кандидаты, JSON по схеме
5. Запись              вердикт + признаки в IndexedDB, тег в Thunderbird
```

Шаг 2 должен снимать 60–80 % писем. Если снимает меньше — чинить признаки,
а не наращивать мощность инференса.

Во внутренней почте заголовков рассылки может не быть вовсе: на живом ящике
22.09.2026 их не оказалось ни у одного из 15 245 дочитанных писем, и отсев
на них дал 5 %. Поэтому главный дешёвый признак в периметре — **поведение
отправителя**: сколько он пишет, отвечает ли в ветке, отвечали ли ему вы,
повторяются ли темы с точностью до номера, сколько у писем получателей. По
этому профилю отправитель относится к системе уведомлений, вещанию на многих
или живым людям (`src/senders.js`), и письма первых двух становятся
информированием без модели. Рядом работают правила адресации (обращаются ко
мне или сообщают в копии), правило «вы уже ответили в этой переписке» — если
в ветке есть ваше письмо позже, действие уже сделано, — и разбор писем о
встречах по приставке в теме: через шлюз Exchange от приглашения остаётся
только «Принято:» или «Новое время:». Исключение — признак действия в теме
(«назначен», «требуется»): такое письмо идёт в модель, потому что поручение
от системы остаётся поручением. Ваши собственные письма участвуют наравне с
входящими: по ним видно, где был разговор, а где вещание.

Оговорка к шагу 2: `List-Unsubscribe`, `Precedence`, `References` и вложения
в `MessageHeader` не приходят. За ними нужен `messages.getFull`, а он читает
письмо целиком и при отсутствии тела офлайн тянет его с сервера. Поэтому
шаг 1 их не заполняет, а ставит `enriched: 0`; полные заголовки читает
отдельный проход обогащения — от свежих писем к старым, архив только в
простое. Письма крупнее порога из настроек не читаются, состав вложений у
них считается неизвестным.

## Модель

- OpenAI-совместимый эндпоинт `/v1/chat/completions`.
- **Не брать рассуждающие модели.** DeepSeek-R1 и его дистилляты выдают
  длинный блок рассуждений перед ответом; на батчевой классификации
  тысяч писем это убивает пропускную способность. Нужна обычная
  instruct-модель 7–14B, либо рассуждение подавляется.
- Формат ответа фиксируется схемой: `response_format: json_schema`, как в
  API OpenAI, — её понимают vLLM, SGLang и сервер llama.cpp. Парсинг
  свободного текста от модели такого размера — источник половины будущих
  багов. Расширение vLLM `guided_json` не использовать: на свежих сборках
  сервер его молча игнорирует, и ответ приходит в произвольном виде (на
  проверке 22.09.2026 — JSON 6 из 6, по схеме 0 из 6).
- Качество на русском проверить на своей выборке. База у дистиллятов
  Qwen, русский у них неровный.

## Проверка качества

Обязательна до включения делегирования и любой работы с устаревшим
информированием.

- `eval/labeled.jsonl` — 300 писем, размеченных вручную по трём классам.
- Метрики: precision и recall по каждому классу.
- Целевой порог: precision на классе «информирование» не ниже 0.95, иначе
  архивирование трогать нельзя. Цена ошибки там выше всего.

## Состояние

Сделан проход по ящику (T1) — то, на чём держится всё остальное.
Перечисление писем окнами по дате, чекпойнты, возобновление после закрытия
клиента, дедупликация по устойчивому ключу, два прохода со свежей почтой
вперёд, выгрузка состояния в JSON, панель с прогрессом и настройки.
Проверен на живом ящике.

Сделан проход обогащения и отсев без модели — гейт (T2). Полные заголовки
дочитываются отдельным проходом из офлайн-хранилища: свежая почта — как
только клиент сохранил её сам, архив — в простое, с возобновлением после
перезапуска. Из письма за одно чтение берутся ветка, признаки
рассылки, вложения, встречи и задачи из приглашений и ссылки на
видеоконференции — ключи, по которым письма, встречи и задачи потом
собираются в дела. Гейт по этим фактам решает очевидное —
рассылки, автоответы, ответы на приглашения, массовые копии — без модели,
у каждого решения есть признаки и цитата. Долю отсеянных писем показывает
страница состояния.

Проверено на стенде: `npm test`, 48 проверок, включая обрыв обоих проходов
с перезапуском клиента и раздачей письмам новых номеров. На живом ящике
проход по 20 000 писем занимает меньше 5 минут, свежий проход за 30 дней —
меньше минуты; обогащение и доля гейта ещё не замерены.

Письма собираются в дела не только по ветке: предмет из темы («Договор № 15»,
INC-0012345) собирает письма разных людей об одном деле, а одинаковая тема при
общем участнике — переписку, у которой не дошли References. Дела
информационных систем свёрнуты под саму систему: её можно развернуть, скрыть
или открыть таблицей «дата — категория — запрос — номер — статус» с выгрузкой
в CSV. Дела можно объединять вручную — перетаскиванием одного на другое на
графе; решение запоминается по ключам писем и переживает пересборку.

Сделана вкладка «Дела» — кнопка на панели пространств клиента. Показываются
дела, в которых было движение за период из настроек (по умолчанию 30 дней),
но собирается каждое с первого письма: ранние письма той же переписки
поднимаются из ящика, и в карточке видна вся история от начала к последней
записи. Письма собираются в дело по ветке, по беседе Outlook, по встрече и
по объекту информационной системы — номеру инцидента или заявки в теме, а без
номера по теме с точностью до чисел. Видеоконференции связывают дела между
собой, а система держит вместе свои дела общим узлом на графе: каждый
инцидент остаётся отдельным делом. Граф на Canvas растёт на глазах, пока
дочитываются новые письма; карточка дела показывает, почему каждое письмо в
нём. Поручения и сроки появятся с подключением модели.

Для проверки сборки на живом ящике есть страница «Отчёт о проверке» (кнопка
в панели): метрики по стадиям собираются сами, ручные проверки отмечаются
там же, итог сохраняется одним файлом. В файле только числа, флаги и
названия полей — без адресов, тем писем и имён серверов.

У дела есть состояние, видное без модели: «Новое» — есть непрочитанное
входящее, «Жду ответа» — последним писали вы, «В работе» — вы в переписке и
последнее письмо прочитано, «Информирование» — уведомления системы, в которые
вы не вступали, «Остыло» — движения давно не было. Состояние красит дело в
списке и на графе; в центре кадра оказывается то, что требует внимания, по
краю — фон. «Поручение», «Просрочено» и «Готово» добавит модель.

Не реализованы: классификация моделью, поручения и состояния дел,
делегирование, работа с устаревшим информированием.

## Сборка

```bash
npm test           # проверки прохода по ящику, зависимостей не требуют
npm run build      # отладочная сборка dist/r7-triage-<версия>-dev.xpi
npm run build:release   # то же с обфускацией, нужен javascript-obfuscator
```

Обфусцированную сборку на addons.thunderbird.net не подпишут: правила
Mozilla разрешают минификацию и запрещают обфускацию. Распространение —
через корпоративные политики.

Установка для разработки: `Инструменты → Отладка дополнений → Загрузить
временное дополнение` → выбрать `manifest.json`.

## Ограничения окружения

- Thunderbird 115.12.2, манифест версии 2. MV3 в этой сборке не
  использовать: персистентный background нужен для длинного прохода.
- Фон объявлен через `background.page`, а не `background.scripts`:
  в MV2 скрипты фона грузятся как классические и `import` в них не работает.
- Расширение — демоверсия на 90 дней. По истечении срока разбор почты
  останавливается, выгрузка накопленного продолжает работать.
- Расширение должно быть подписано для постоянной установки. Уточнить
  политику подписи в вашей сборке Органайзера.
- В профиле возможны другие расширения, удерживающие сетевые перехватчики.
  При добавлении собственных проверять на конфликты.
